# 编写新故事

## 输入

调用方通过 prompt 传入创意简报，包含：
- **主题**：故事主题或用户的原始描述
- **风格**：视觉风格关键词（如"手绘插画、暖色调、童话风"）
- **时长**：目标视频时长（如"1min"、"3min"）
- **画面比例**：如 16:9 或 9:16
- **语言**：对白语言（如"中文"、"英文"）
- **项目路径**：故事文件的输出目录（绝对路径）

如有 `<file>` 标签注入已有故事文件，说明是在已有基础上续写或重写。

## 步骤

### Step 1: 估算故事容量

根据时长估算故事规模：

| 时长 | 场景数 | 角色数（建议） | 幕数 |
|------|--------|---------------|------|
| 30s | 2-3 | 2-3 | 1 |
| 1min | 3-6 | 3-5 | 1-2 |
| 3min | 8-15 | 4-8 | 2-3 |
| 5min+ | 15+ | 不限 | 3+ |

每个场景约对应 1-3 个 shot，每个 shot 5-10 秒。这是硬约束——故事不能超出时长承载力。

画面比例影响叙事：
- **竖屏 (9:16)**：适合单人特写、纵向空间、近距离情感
- **横屏 (16:9)**：适合多人互动、环境交代、横向运动

### Step 2: 写 meta.json 并推导视觉世界规则

`{project_path}/meta.json` 包含：
- `title`：故事标题
- `video_info`：`aspect_ratio`、`duration`、`language`（从创意简报提取）
- `style`：`style_prefix`、`negative_prefix`（从创意简报提取）

写完 meta.json 后，根据 style_prefix 推导本项目的**视觉世界规则**：画面质感、光影风格、色调、材质表现。风格决定事物**看起来**怎样（渲染方式），主题决定故事里**有什么**（角色、世界观）。后续所有视觉设计（角色 fixed_traits、地点 description、道具 description、场景 appearance）用视觉世界规则决定画面质感，用主题决定角色和世界的本体设定。

### Step 3: 设计叙事骨架

先确定故事的**结构骨架**（哪里是转折、哪里是高潮），再往里面填场景。

#### 3.1 规划叙事骨架

在构思具体场景之前，先列出故事的**关键叙事节点**：

1. **起点**：故事从什么状态开始？观众需要知道什么？
2. **转折点**：哪些时刻故事走向发生不可逆变化？（通常 1-2 个）
3. **高潮**：情绪最高点在哪里？
4. **终点**：故事以什么状态结束？

然后为每个节点标注 `narrative_weight`：
- **climax**：情绪最高点（整个故事通常只有 1 个）
- **turning_point**：故事走向发生不可逆变化的时刻
- **setup**：建立信息、铺垫冲突
- **transition**：连接两个重要时刻的过渡

#### 3.2 设计场景序列（因果链驱动）

**不要先列出所有场景再检查因果关系。而是从起点出发，逐个推导下一个场景。**

维护一个**观众认知状态**——观众到目前为止看到了什么、知道了什么。然后对每个场景：

```
观众认知状态 = {故事起始条件}

for each 叙事节点（按时间顺序）:
  1. 这个节点需要观众已经知道什么？
  2. 当前"观众认知状态"是否已包含这些信息？
  3. 如果有缺口 → 在中间插入场景来补齐缺口
     典型缺口：
     - 角色状态突变无过程（睡着 → 在跑，中间缺"惊醒"）
     - 角色空间跳跃无交代（在 A 地 → 在 B 地，中间缺"移动/转场"）
     - 决策无动机（角色突然行动，观众不知道为什么）
     - 时间跳跃无线索（morning → afternoon，观众感知不到流逝）
  4. 缺口补齐后，写出当前场景
  5. 更新"观众认知状态"
```

#### 3.3 写 outline.json

将 3.2 的结果写入 `{project_path}/outline.json`：
- `acts` 数组（短故事 1-2 幕，长故事按需增加）
- 每幕包含 `id`、`title`、`summary`、`scenes` 数组
- 每场景包含 `id`、`title`、`summary`、`location`、`characters`、`time_of_day`、`mood`、`narrative_weight`
- 可选字段：`area`、`period`、`thread`、`narrative_mode`（不需要时不填）
- 超长故事（5+ 幕）可使用 `parts` 包裹 `acts`

**场景 ID 规则**：`scene_001`、`scene_002`... 全局递增。

### Step 4: 从大纲提取实体

outline.json 已确定所有场景、角色、地点。现在从大纲中提取实体，写入 `{project_path}/entities.json`。

本步骤所有视觉描述（fixed_traits、location description、prop description）必须在 Step 2 推导的视觉世界规则内设计。

#### 4.1 提取角色（characters）

遍历 outline.json 所有场景的 `characters` 字段，收集去重后的角色 ID 列表。为每个角色设计：

- `fixed_traits`：**必须具体且有区分度**，且必须是视觉世界规则下物理上可信的特征。区分度应通过风格允许的手段实现。
- `relationships`：引用 outline.json 中已确认的 scene ID（`from`/`until`），不要引用不存在的场景。

#### 4.2 提取地点（locations）

遍历 outline.json 所有场景的 `location` 字段，收集去重后的地点 ID 列表。为每个地点设计：

- `description`：地点的**默认视觉描述**——物理空间的固定特征（建筑结构、植被、地形）。不要写进光照、天气等会随场景变化的内容，那些属于 location_state。
- `areas`：只在同一地点有多个会被具体使用的子区域时才添加。

#### 4.3 提取道具（props）

从大纲场景的 summary 和角色设定中提取叙事中有重要作用的道具。不需要列出所有出现过的物品——只提取对剧情推进或视觉标识有意义的道具。

#### 4.4 写入 entities.json

将 4.1-4.3 的结果写入 `{project_path}/entities.json`。

### Step 5: 编写场景详情

逐幕编写详细的场景内容，写入 `{project_path}/act-{N}.json`（N 为幕序号，从 1 开始）。

每个场景包含：
- `description`：场景的环境描写（视觉细节，光影，氛围）
- `characters_present`：在场角色 ID 列表
- `character_states`：每个角色在该场景的 `emotion` 和 `appearance`（外观无变化时为 null）
- `location_state`：地点在该场景的 `appearance` 和 `lighting`（无特殊变化时为 null）
- `props_in_scene`：出现的道具 ID 列表
- `prop_states`：道具在该场景的状态（无变化时为 null）
- `beats`：场景内的叙事节拍序列

**beats 写作要点：**
- `type: "action"`：描述观众看到的动作和画面（可见的行为，不是内心活动）
- `type: "dialogue"`：角色对白，含 `speaker`（角色 ID 或 "narrator"）、`text`、`tone`
- 按时间顺序排列，每个 beat 是一个叙事最小单元
- action 句子必须完整（主谓宾）：写明谁做了什么。"小红帽弯腰摘了几朵野花" 而非 "小红帽在路边玩耍"；"老奶奶推开木门走进屋内" 而非 "木门被推开"
- 旁白（narrator）用于补充无法通过画面直接表达的信息，尽量少用

**编写时持续维护观众认知状态：** 每写完一个场景的 beats，确认观众在看完这些 beats 后，已掌握理解下一场景所需的全部信息。如果发现缺口，立即补充 beat 或回到 Step 3.2 插入桥接场景。

### Step 6: 自检

写完所有文件后，逐项检查：

1. **空间连贯**：角色只在其所在场景中行动，场景转换有逻辑
2. **时间线合理**：`time_of_day` 和 `period` 前后不矛盾
3. **角色一致**：`characters_present` 与 beats 中出场的角色一致
4. **状态显式**：所有视觉变化（换装、受伤、环境变化）都在对应的 states 中声明，且所有视觉描述在 Step 2 的视觉世界规则内可信
5. **ID 引用正确**：所有角色/场景/道具 ID 在 entities.json 中存在
6. **对白语言**：对白语言与 meta.json 中的 `language` 一致
7. **时长匹配**：场景总数与 Step 1 的估算大致吻合
8. **narrative_weight 合理**：climax 通常只有 1 个，turning_point 不超过 2-3 个，不存在全部标为 setup 的情况

发现问题直接修复，不需要报告给调用方。

## 输出

在项目路径下生成以下文件（按写入顺序）：
- `meta.json` — 标题、视频规格、风格
- `outline.json` — 故事大纲（幕 → 场景摘要）
- `entities.json` — 角色、地点、道具（从大纲提取）
- `act-1.json`、`act-2.json`... — 各幕场景详情

## 错误处理

- **创意简报信息不全**：缺少主题则无法执行，报告调用方。缺少时长/比例/语言可用合理默认值（1min / 16:9 / 中文）但在输出中标注。
- **WriteFile 失败**：重试 1 次。连续失败则报告调用方。
- **故事过于复杂超出时长**：主动缩减场景数量或拆分为多集（告知调用方）。
