# 编写新故事

## 输入

调用方通过 prompt 传入创意简报，包含：
- **主题**：故事主题或用户的原始描述
- **风格**：视觉风格关键词（如"手绘插画、暖色调、童话风"）
- **时长**：目标视频时长（如"1min"、"3min"）
- **画面比例**：如 16:9 或 9:16
- **语言**：对白语言（如"中文"、"英文"）
- **项目路径**：故事文件的输出目录（绝对路径）

如有 `<file>` 标签注入已有故事文件，说明是在已有基础上续写或重写。

## 步骤

### Step 1: 估算故事容量

根据时长估算故事规模：

| 时长 | 场景数 | 角色数（建议） | 幕数 |
|------|--------|---------------|------|
| 30s | 2-3 | 2-3 | 1 |
| 1min | 3-6 | 3-5 | 1-2 |
| 3min | 8-15 | 4-8 | 2-3 |
| 5min+ | 15+ | 不限 | 3+ |

每个场景约对应 1-3 个 shot，每个 shot 5-10 秒。这是硬约束——故事不能超出时长承载力。

画面比例影响叙事：
- **竖屏 (9:16)**：适合单人特写、纵向空间、近距离情感
- **横屏 (16:9)**：适合多人互动、环境交代、横向运动

### Step 2: 设计世界设定

构思角色、场景、道具，然后写入 `{project_path}/entities.json`。

**角色设计要点：**
- `fixed_traits` 必须具体、有区分度（"红色丝绒斗篷，白色连衣裙" 而非 "穿着裙子"）
- 避免外形相似的角色（AI 生成难以区分）
- `tags` 标注角色维度（角色类型、阵营、家族等）
- `relationships` 标注角色间关系，有变化的关系用 `from`/`until` 标注时间范围

**场景设计要点：**
- 每个场景的 `description` 要描述可见的环境细节
- 如果同一地点有多个明确的子区域会被用到，添加 `areas`
- 场景数量要适度——太多增加视觉不一致风险

**道具设计要点：**
- 只创建推动剧情的关键道具
- `belongs_to` 标注初始归属

### Step 3: 设计故事大纲

构思幕和场景结构，写入 `{project_path}/outline.json` 和 `{project_path}/meta.json`。

**meta.json** 包含：
- `title`：故事标题
- `video_info`：`aspect_ratio`、`duration`、`language`（从创意简报提取）
- `style`：`style_prefix`、`negative_prefix`（从创意简报提取）

**outline.json** 包含：
- `acts` 数组（短故事 1-2 幕，长故事按需增加）
- 每幕包含 `id`、`title`、`summary`、`scenes` 数组
- 每场景包含 `id`、`title`、`summary`、`location`、`characters`、`time_of_day`、`mood`
- 可选字段：`area`、`period`、`thread`、`narrative_mode`（不需要时不填）
- 超长故事（5+ 幕）可使用 `parts` 包裹 `acts`

**场景 ID 规则**：`scene_001`、`scene_002`... 全局递增。

**大纲设计要点：**
- 每个场景有明确的叙事功能（引入角色、推动冲突、转折、高潮、结局）
- 场景之间的空间转换要有逻辑（角色不能凭空出现在另一个地点）
- `mood` 描述场景的整体情感氛围，供后续 DP 和声音设计参考

### Step 4: 编写场景详情

逐幕编写详细的场景内容，写入 `{project_path}/act-{N}.json`（N 为幕序号，从 1 开始）。

每个场景包含：
- `description`：场景的环境描写（视觉细节，光影，氛围）
- `characters_present`：在场角色 ID 列表
- `character_states`：每个角色在该场景的 `emotion` 和 `appearance`（外观无变化时为 null）
- `location_state`：地点在该场景的 `appearance` 和 `lighting`（无特殊变化时为 null）
- `props_in_scene`：出现的道具 ID 列表
- `prop_states`：道具在该场景的状态（无变化时为 null）
- `beats`：场景内的叙事节拍序列

**beats 写作要点：**
- `type: "action"`：描述观众看到的动作和画面（可见的行为，不是内心活动）
- `type: "dialogue"`：角色对白，含 `speaker`（角色 ID 或 "narrator"）、`text`、`tone`
- 按时间顺序排列，每个 beat 是一个叙事最小单元
- action 要具体："小红帽弯腰摘了几朵野花" 而非 "小红帽在路边玩耍"
- 旁白（narrator）用于补充无法通过画面直接表达的信息，尽量少用

### Step 5: 自检

写完所有文件后，逐项检查：

1. **因果链完整**：每个事件都有前因后果，不存在突然出现的情节
2. **空间连贯**：角色只在其所在场景中行动，场景转换有逻辑
3. **时间线合理**：`time_of_day` 和 `period` 前后不矛盾
4. **角色一致**：`characters_present` 与 beats 中出场的角色一致
5. **状态显式**：所有视觉变化（换装、受伤、环境变化）都在对应的 states 中声明
6. **ID 引用正确**：所有角色/场景/道具 ID 在 entities.json 中存在
7. **对白语言**：对白语言与 meta.json 中的 `language` 一致
8. **时长匹配**：场景总数与 Step 1 的估算大致吻合

发现问题直接修复，不需要报告给调用方。

## 输出

在项目路径下生成以下文件：
- `meta.json` — 标题、视频规格、风格
- `entities.json` — 角色、场景、道具
- `outline.json` — 故事大纲（幕 → 场景摘要）
- `act-1.json`、`act-2.json`... — 各幕场景详情

## 错误处理

- **创意简报信息不全**：缺少主题则无法执行，报告调用方。缺少时长/比例/语言可用合理默认值（1min / 16:9 / 中文）但在输出中标注。
- **WriteFile 失败**：重试 1 次。连续失败则报告调用方。
- **故事过于复杂超出时长**：主动缩减场景数量或拆分为多集（告知调用方）。
