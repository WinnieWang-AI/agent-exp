# 修改策略：路由 → 执行 → 传播

用户交付成片后要求修改时，加载本文件。不预判完整回退链，按三步反应式处理。

## 步骤

### Step 1: 路由——判断入口 agent

根据用户反馈内容，确定第一个需要接收修改的 agent：

| 用户反馈涉及 | 入口 agent |
|-------------|-----------|
| 故事情节、角色设定、场景增删 | 编剧 |
| 镜头构图、运镜、时长分配、音频策略、角色外观/状态描述 | 导演 |
| 参考图风格、角色形象、场景画面设计 | 美术 |
| 视频画面质量、动作表现、视觉一致性 | 摄影 |
| 背景音乐风格、节奏 | 作曲 |
| 转场、剪辑节奏、字幕、音视频同步 | 剪辑 |

如果不确定归谁，转给导演——导演是创作决策的中枢，能判断问题出在哪个环节。

### Step 2: 执行——让入口 agent 处理

用同一 session_id 调度入口 agent，将用户的原始反馈转达。

agent 自主决定改什么、怎么改，完成后报告**实际变更了哪些文件**。

### Step 3: 传播——沿依赖链触发下游

根据入口 agent 报告的实际文件变更，沿依赖链触发需要重做的下游 agent：

```
剧本文件 → 导演 → 美术(参考图) → 摄影 → 剪辑
                                → 作曲 → ┘
```

传播规则：
- 剧本文件变了（entities/outline/act-N）→ 重新调度导演（说明剧本已更新，重传 context_files）→ 导演产出变了则继续往下
- events/states/shots 变了 → 看具体变更：只改了事件情绪/描述则重做作曲，改了视觉描述则重做美术+摄影
- 参考图变了 → 摄影重拍引用了该参考图的 shot
- 视频片段变了 → 剪辑重新组装
- 只改了组装参数 → 只重做剪辑

**每次传播只触发直接受影响的下游**，不"保险起见"全部重来。如果不确定某个下游是否受影响，在 prompt 中把变更内容告诉下游 agent，让它自己判断。

### Step 4: 重新组装

只要有视频或音频变更，最后都调度剪辑重新组装。输出路径递增规则同 workflow-execution Step 3。
