# Agent System Prompt 写作规范

本文档规定所有 agent 的 system prompt 文件结构、命名规范和写作原则。新建或重构 agent 时必须遵循。

## 文件分层

每个 agent 的 prompt 内容分为三层，按需加载：

| 层级 | 文件 | 内容范围 | 体积约束 |
|------|------|---------|----------|
| **L0: 身份** | `system.md` | 角色定义、能力边界、工作流概览、核心规则 | ≤ 800 words |
| **L1: 流程** | `workflow-{phase}.md` | 阶段详细步骤、输入输出规格、判断逻辑、错误处理 | 按需 |
| **L2: 参考** | `guide-{topic}.md` | 示例、prompt 模板、评估标准等参考资料 | 按需 |

核心原则：**system.md 只回答"我是谁、我能做什么、大致怎么做"，不回答"具体怎么做的每个细节"。**

## system.md 固定结构

```markdown
# {Agent Name}

{一句话角色定义}

${ROLE_ADDITIONAL}

## 能力边界

- 我负责：...
- 我不负责：...
- 我有哪些工具：...

## 工作流概览

{按阶段列出高层步骤，每步一行，不展开细节}

本 agent 的 L1/L2 文件：
- `${AGENT_DIR}/workflow-{name}.md` — {一句话说明}
- `${AGENT_DIR}/guide-{name}.md` — {一句话说明}

## 核心规则

{不超过 5 条，只放绝对不能违反的硬性约束}

## 工作环境

- Current date: ${KIMI_NOW}
- Working directory: ${KIMI_WORK_DIR}

${KIMI_AGENTS_MD}
```

### system.md 中禁止出现的内容

- 具体的工具调用示例（放 L1）
- Prompt 写作规范和示例（放 L2）
- 详细的错误处理策略（放 L1）
- 数据结构定义和字段说明（放 L1）
- 超过 3 行的代码块（放 L1）

## L1 流程文件

### 命名规范

`workflow-{phase}.md`，每个文件对应工作流的一个阶段。文件名使用短横线分隔的英文小写。

示例：
```
workflow-plan.md        # 制定计划阶段
workflow-generate.md    # 执行生成阶段
workflow-assemble.md    # 组装阶段
```

### 内部结构

```markdown
# {Phase Name}

## 输入

{该阶段需要什么数据、从哪来}

## 步骤

{详细步骤，含工具调用示例和判断逻辑}

## 输出

{该阶段产出什么、写到哪}

## 错误处理

{该阶段特有的错误恢复策略}
```

## L2 参考文件

### 命名规范

`guide-{topic}.md`，纯参考资料，不含流程逻辑。文件名使用短横线分隔的英文小写。

示例：
```
guide-prompt-video.md      # 视频 prompt 写作规范
guide-shot-strategy.md     # 镜头策略参考
guide-eval-criteria.md     # 评估标准
```

### 内部结构

无固定模板，按内容组织。但必须满足：
- 开头一句话说明本文件的用途和加载时机
- 有示例时用 `<example>` 标签包裹
- 不包含流程逻辑（流程在 L1 中）

## 写作原则

1. **一个信息只出现在一个地方。** 如果 L1 里写了详细步骤，system.md 只放一行概览，不重复。违反此原则会导致修改时遗漏同步，产生不一致。

2. **每个文件有明确的读者和时机。** 写之前先问：谁在什么时候需要读这个？如果答不上来，这个信息可能不需要单独成文件。

3. **示例跟着操作走。** 示例放在对应的 L1/L2 文件中，不放 system.md。system.md 中的示例只会浪费每一轮对话的 token。

4. **规则按作用域分层。** 全局硬约束（如"禁止编造"、"禁止本地生成"）放 system.md 的核心规则。阶段性规则（如"并行最多 5 个 shot"）放对应的 L1 文件。

5. **控制 system.md 体积。** system.md 每次对话的每一轮都会被加载。800 words 以内。超出时审视：哪些内容可以下沉到 L1/L2？

6. **L1/L2 文件名自解释。** 看到文件名就知道内容和加载时机，不需要额外的索引文档。

7. **L2 示例精简。** 每个 guide 文件保留 ≤ 1 个典型示例，用 `<example>` 包裹。多个示例覆盖不同 case 时，拆到独立文件（如 `examples-{topic}.md`），workflow 在遇到对应 case 时才 ReadFile 加载。示例的目的是建立格式认知，不是穷举所有场景。

8. **继承即开销。** `extend` 引入的父级 system.md 内容计入 L0 体积预算。如果父级内容对当前 agent 大部分无关（如通用编码指南对视频制作 agent），应通过中间层隔离——创建领域 base agent，只继承相关的基础规则，屏蔽无关内容。

9. **长会话 agent 必须配 compact.md。** 会话中产生大量中间状态的 agent（逐 shot 生成、多步组装、多轮迭代评估）需要配置 `compaction_prompt_path`，定义上下文压缩时必须保留的关键信息（项目标识、当前进度、已完成/失败的 shot 列表等）和可丢弃的信息（已完成 shot 的详细 prompt、中间文件路径等）。

10. **规则说做什么，不说不做什么。** 修改 prompt 时，用正向描述定义行为（"原样传递用户的故事描述"），不用负向补丁禁止具体错误（"不要加'现代'"）。负向补丁只封堵已知 case，正向规则覆盖所有 case。

11. **规则描述边界，不绑定 case。** 规则应当是从问题中提炼的通用原则，不是对某次具体错误的针对性修补。如果一条规则只在遇到过的那个 case 上生效，说明抽象层级不够。
